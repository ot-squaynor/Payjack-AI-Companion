# PayJack AI - Data and Knowledge Base File and Folder Strategy

This document explains the **file and folder strategy** used for datasets, documentation, runtime modules, scripts, tests, and infrastructure in the PayJack AI repository.

The system separates information into two distinct layers:

| Layer | Folder | Purpose |
|------|------|------|
| **Knowledge Retrieval (RAG)** | `backend/kb/` | Documentation used by the LLM for answering informational questions |
| **Structured Data (Tools)** | `backend/data/` | Structured datasets queried directly by deterministic tools |

This separation ensures:

- PII and financial data are **never retrieved via RAG**
- Documentation retrieval remains **safe and explainable**
- Financial data queries remain **deterministic and auditable**

---

# 1. Knowledge Base (`backend/kb/`)

The **Knowledge Base** contains documentation that the AI retrieves using **RAG (Retrieval Augmented Generation)**.

Examples include:

- Help center articles
- Product features
- Fees explanations
- Limits explanations
- Error explanations

These documents contain **no customer-specific information**.

---

    |-- features/

# 1.2 `backend/kb/raw_docs/`

This folder contains the **original knowledge documents** before processing.

Documents here may come from:

- Help center exports

Files in this folder are later **cleaned, chunked, and embedded** into retrieval artifacts.

# 2. Structured Data (`backend/data/`)

The `backend/data/` directory contains structured datasets used by the assistant tools.

These datasets contain financial information and may contain sensitive data.

The AI does not retrieve these via RAG.

Instead they are queried through deterministic tools such as:

- `transaction_lookup`
- `spend_summary`
- `balances`

---

    |-- accounts/

# 3. Current Backend Runtime Folder Strategy

The runtime backend is separated by responsibility so the system remains auditable and maintainable.

## 3.1 `backend/app/data_pipeline`

| Folder | File/module | Purpose | Runtime or offline | Why it exists |
|--------|-------------|---------|--------------------|---------------|
| `backend/app/data_pipeline` | `ingestion.py` | Loads local and S3 raw source files, parses them, standardizes schema, and deduplicates rows | Offline | Turns heterogeneous raw exports into a consistent starting point |
| `backend/app/data_pipeline` | `normalization.py` | Cleans canonical fields, normalizes merchants/categories/currency, and derives helper fields | Offline | Makes downstream tool logic and analytics consistent |
| `backend/app/data_pipeline` | `category_mapping.py` | Applies deterministic taxonomy and alias/rule-based category mapping | Offline | Keeps categorization auditable and non-LLM |
| `backend/app/data_pipeline` | `recurring_logic.py` | Detects cadence, groups repeating patterns, and assigns recurrence confidence | Offline | Supports recurring-payment explanations without model guesses |
| `backend/app/data_pipeline` | `quality_checks.py` | Runs deterministic QC over processed outputs and emits a machine-readable report | Offline | Prevents bad artifacts from entering runtime |
| `backend/app/data_pipeline` | `processed_schema.py` | Defines processed artifact and manifest contracts | Offline and runtime-adjacent | Locks the handoff between pipeline and runtime |

## 3.2 `backend/app/tools`

| Folder | File/module | Purpose | Runtime or offline | Why it exists |
|--------|-------------|---------|--------------------|---------------|
| `backend/app/tools` | `transaction_lookup.py` | Returns filtered transaction views for user questions | Runtime | Core deterministic transaction access |
| `backend/app/tools` | `spend_summary.py` | Aggregates spend by time/category/filter set | Runtime | Answers common spending questions deterministically |
| `backend/app/tools` | `recurring_detection.py` | Returns recurring-payment summaries from processed recurrence signals | Runtime | Reuses offline recurrence enrichment in a user-facing form |
| `backend/app/tools` | `balances.py` | Returns balance-related structured summaries where data is available | Runtime | Separates balance logic from orchestration |
| `backend/app/tools` | `status_explanation.py` | Interprets transaction/account status values deterministically | Runtime | Keeps status explanations rule-based |
| `backend/app/tools` | `registry.py` | Registers tools and standardizes invocation/response contracts | Runtime | Gives the orchestrator one tool interface |

# 6. Processed Artifact Contract

The offline pipeline produces a runtime-ready processed artifact bundle.

| Artifact | Purpose | Consumed by |
|----------|---------|-------------|
| `*.parquet` | Canonical processed datasets such as transactions and accounts | Repository layer and deterministic tools |
| `manifest.json` | Declares dataset version, artifact paths, source metadata, and build metadata | Repository layer, runtime health, and audits |
| `qc_report.json` | Machine-readable data quality results | Developers, pipeline validation, and QA checks |
| `pipeline_summary.json` | Human-readable or summarized pipeline run outputs | Local inspection and operational review |

These artifacts are created offline by `scripts/dataset_transform.py` and loaded at runtime through `backend/app/repository/processed_store.py`.

# 9. S3 and Bucket Mapping

S3 usage is intentionally split by ownership and lifecycle.

## 9.1 External Raw Buckets

These are referenced but not created or destroyed by the environment stack.

| Bucket type | Ownership model | Notes |
|-------------|-----------------|-------|
| Transactions | External | Source input only |
| Accounts | External | Source input only |
| Fees and limits | External / optional | Referenced if available |
| Products | External / optional | Referenced if available |
| Metadata | External / optional | Referenced if available |

## 9.2 Managed Environment Buckets

These are created by the environment stack.

| Bucket type | Lifecycle | Notes |
|-------------|-----------|-------|
| Processed artifacts | Environment-managed | Holds transformed data outputs for runtime |
| Frontend bucket | Optional environment-managed | Used only if static frontend hosting is added |

## 9.3 Shared Create-Once Buckets

These are created by the bootstrap stack and should survive normal environment destroy flows.

| Bucket type | Lifecycle | Notes |
|-------------|-----------|-------|
| KB source bucket | Shared / create-once | Stores `raw_docs/...` |
| KB artifacts bucket | Shared / create-once | Stores environment-prefixed processed docs and metadata |

## 9.4 Prefix Strategy

Current prefix layout:

| Bucket | Prefix pattern | Purpose |
|--------|----------------|---------|
| Shared KB source bucket | `raw_docs/errors/` | Error documentation |
| Shared KB source bucket | `raw_docs/features/` | Feature documentation |
| Shared KB source bucket | `raw_docs/fees/` | Fee documentation |
| Shared KB source bucket | `raw_docs/help_center/` | Help-center documentation |
| Shared KB source bucket | `raw_docs/limits/` | Limits documentation |
| Shared KB artifacts bucket | `<env>/processed_docs/` | Chunked and embedding outputs |
| Shared KB artifacts bucket | `<env>/metadata/` | KB manifests and metadata |
| Managed processed bucket | `<env>/` or configured processed prefix | Processed financial artifacts |

This structure ensures:

- Knowledge content stays separate from structured financial data
- External source buckets remain unmanaged
- Shared KB buckets are not destroyed with normal dev/test teardown

# 12. Documentation Rules for This Repo

To keep repo documentation auditable:

- Architectural trees should exclude generated and local-only folders such as `.venv`, `.next`, `node_modules`, `coverage`, `.pytest_tmp`, `__pycache__`, and `.terraform`
- Unimplemented integrations should be labeled **optional** or **future**, not implied as current
- KB documentation and structured financial data should always be documented separately
- Runtime modules, offline pipelines, and infrastructure should remain separated in folder descriptions

# Key Rule

KB = RAG retrieval for documentation

DATA = deterministic tool queries for structured financial data

This design ensures:

- Customer data stays secure
- Retrieval remains accurate
- Tool outputs remain deterministic
- The AI does not hallucinate financial data
